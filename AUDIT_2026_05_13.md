## Critical — block live trading

- [x] **CORE_ALLOC_CAP fix is uncommitted; live bot is currently emitting
  2.0× the documented exposure.** The `_cap_core_weights()` function and
  the `today_inputs()` cap (`jplus/simulate.py:46-67`, `jplus/simulate.py:351-358`)
  exist only in the working tree — no commit, no deploy. Live `dashboard.db`
  shows `SJ-3449 JPLUS_R4_ETH ETH LONG allocation_pct=40.0 leverage=5.0
  size_usdt=$20,000` opened 2026-05-12 on a $10,000 variant. That is the
  exact pathology the cap was written to prevent (per the inline comment
  at `jplus/simulate.py:51-54`, the audit memory at
  `memory/feedback_allocation_and_sl_policy.md`, and the
  `register_p300.py` PDO 11%→9% trim). Until the working tree is
  committed and `run.py` restarted, every per-tick read of
  `today_inputs()` continues to return uncapped weights. **Action:**
  commit and restart before any further live SHADOW accumulation — this
  audit cannot trust forward shadow numbers from before that cutover.

## High — real inflation, not yet documented

- [x] **No slippage, bid-ask spread, or market-impact model anywhere in
  the fill path.** `services/price_feed.get_current_price` returns the
  last *closed* 1m bar's close (good for look-ahead, neutral for
  reality), and both `trades.open_shadow_trade` and `trades.close_perp_trade`
  use that close as the fill price unchanged. Real Binance BTC/USDT
  retail fills on a market order cost ~3–5bp spread + 1–2bp slippage on
  $1–$20k notional, more in volatile windows. PORTFOLIO.md §7 lists
  every other in-sample-bias caveat but has no fee/spread caveat for the
  *execution* path — only for fees-bp charged via `DEFAULT_COST_BP_RT`.
  Estimated systematic over-report: 5–10bp per round-trip × 100s of
  trades/year. (`services/price_feed.py:59-95`,
  `services/trades.py:94-179`, `services/trades.py:194-241`)

- [x] **`full_portfolio_report.py` compounds fixed-capital daily returns
  → Jensen's gap inflates total return / CAGR / MDD.** `trades_daily_returns`
  (`services/strategy_health.py:156-209`) computes daily return as
  `sum(pnl_usdt) / capital × 100`, where `capital` is the *constant*
  starting variant capital (positions are also sized off this fixed
  capital — `services/trades.py:130-132`). `tools/full_portfolio_report.py`
  then `compound_equity()` walks these as `eq *= (1 + r/100)`
  (`tools/full_portfolio_report.py:88-95`). That's geometric growth
  applied to arithmetic returns; final equity overstates real cash growth
  by ~nσ²/2 — for σ≈1%/day, that's ~+1.8%/yr in reported total return,
  ~+4–5% over the 2.66y window, plus CAGR drift in the same direction
  and a systematically *smaller* MDD on positive-drift windows. The
  fix is summation, not compounding — equivalent to what `backtest_runner.compute_metrics`
  already does correctly (`backtest_runner.py:339-380`). Same defect
  poisons the live startup banner via
  `services.strategy_health.portfolio_metrics → cumulative_return_pct`
  (`services/strategy_health.py:260, 65-70`).

- [x] **`tools_statistical_validation.py` reads from a table no longer
  written.** The headline number in README.md:13 (`Sharpe ≈ 1.73 with
  bootstrap 95% CI of [0.96, 2.44]`) is documented as the output of
  `python tools/tools_statistical_validation.py`. The tool's
  `load_returns()` at `tools/tools_statistical_validation.py:29-37`
  reads `variant_daily_returns WHERE source='replay'`, but the
  trade-emitter migration (commits `d394ec1`, `d70cd4b`, `c4e4363` from
  Phase 3–5) removed every production writer to that table —
  `INSERT INTO variant_daily_returns` is now grep-clean except for
  `tests/test_strategy_health.py`. The tool prints
  `"No replay returns found"` on a fresh `dashboard.db`. The README CI
  is **stale and unreproducible from current code**, and the tool itself
  needs to be migrated to read from `trades_daily_returns` (or deleted
  if the migration is too involved). At minimum, the README claim should
  be retracted until the tool works again.

- [x] **Live mode never runs the liquidation simulator.** Per the
  README §"Which sim tool" table at lines 209-218 — `run.py --mode sim`
  is "NO" on liquidation checks; only `backtest_runner.py` runs
  `check_liquidations_for_variant`. That means **(a)** the live SHADOW
  ledger forward from go-live will not show liquidations even at trades
  where the position would have been wiped on a real exchange, and
  **(b)** parity tests between `run.py --mode sim` and
  `backtest_runner.py` (`tests/test_sim_mode.py`) are byte-identical only
  *because* both modes skip non-strategy-driven closes for the J+ sleeves
  — that parity does not certify either path against actual execution.
  The simulator exists at `services/margin_sim.py` + `services/margin_check.py`;
  wiring `check_liquidations_for_variant` into the live tick of
  `services/variant_engine.py` and into `services/sim_loop.run_sim` would
  close the gap. Until then, README §"Status" line 10 ("Live SHADOW
  accumulation is the only real OOS validation path") is materially weakened —
  SHADOW PnL is liquidation-blind, so an apparent +X% on a 10× FOMC
  sleeve would have been a -100% (account wipe) in reality at the
  adverse intra-bar mark.

- [x] **Margin simulator's collateral haircut and margin-mode mismatch
  reality.** `SimParams.spot_haircut = 0.95` (`services/margin_sim.py:217`)
  — Binance's USDM cross-margin collateral ratio for BTC spot is ~0.50
  (capital-letter "Collateral Margin Ratio" in the futures portfolio
  page, 0.7 at the higher tier). Using 0.95 overstates CARRY's
  cross-margin pool by ~80% and underreports liquidation risk on
  CARRY-style hedge positions. Separately, `margin_check.py:196` defaults
  every non-CARRY sleeve to `MarginMode.ISOLATED`, but the saved go-live
  plan (per `memory/project_margin_mode_design.md`) is cross for every
  sleeve except FOMC. Isolated is *stricter* than cross (no spot/perp
  netting), so this direction over-reports liquidations slightly while
  the haircut under-reports them — they don't cancel, they apply to
  different sleeves. Effect on SHADOW numbers is bounded by how
  near-liquidation any position gets, but the simulator is currently
  not modeling the configuration the live bot will run under.

- [x] **`apply_r4_fees()` uses raw regime weights, not capped weights.**
  `jplus/simulate.py:376-382` keeps an inline duplicate of regime weights
  (`_REGIME_R4_WEIGHTS`) that was the pre-2026-05-12 raw table. The
  simulator loop now uses `_cap_core_weights(REGIME_WEIGHTS_FULL[mode])`
  (capped), but `apply_r4_fees` at lines 408-422 still reads the raw
  duplicate and computes `fee_pct = weight × r4_lev × vol_target_lev × fee_frac`
  — i.e. fees on hypothetical 40%-of-capital R4_ETH positions when the
  simulator-side P&L was already sized at the capped 14.8%. Result: any
  research consumer who calls `apply_r4_fees` on `simulate()` output
  subtracts 2–3× too much in fees. The fee helper is described as
  research-only (no runtime call), but anyone running parameter sweeps
  to compare to legacy numbers will see depressed returns from this
  asymmetry. Also the docstring comment at line 374 ("hot path doesn't
  want a dict lookup") is no longer accurate — the loop at line 194
  *does* do a dict lookup. (`jplus/simulate.py:373-424`)

- [x] **EMA_BTC / ETH_DAILY closes zero out fees AND funding on live
  closes of perpetual positions.** `services/jplus_live.py:419-424` and
  lines 544-549 call `close_perp_trade(..., cost_bp_rt=0.0,
  apply_funding=False)`. PORTFOLIO.md §3 "Cost migration" documents this
  for ETH_DAILY as "remains zero-fee in the simulator and live handler
  pending a spot-fee model" but ETH_DAILY trades the **perp** (per
  PORTFOLIO.md table at line 192 "ETH" / continuous in bull regimes),
  not spot — so the zero-funding default is structurally wrong, not a
  pending-fee-model issue. A multi-week ETH-LONG perp at 8h funding
  averaging ~0.005% = 4.5%/yr can swing realized P&L by several percent
  per held position. EMA_BTC is similar — continuous perp, no funding
  accrual on close. Magnitude is large on long holds: an EMA_BTC SHORT
  through a high-funding regime collects funding income that's currently
  invisible. Flag this as either (a) a real inflation/deflation source
  to track, or (b) a deliberate model simplification — but the
  PORTFOLIO.md framing reads as if it's only a *fee* issue, missing the
  funding half.

- [x] **Funding load swallows DB errors silently.** `services/trades.py:226-230`
  wraps the funding lookup in `try / except (TypeError, ValueError)`
  and falls back to `funding_pct = 0.0` with no log. A
  `sqlite3.OperationalError` (table missing, DB locked) bubbles up
  *outside* that except clause, but the `_connect_or_warn` helper at
  `services/funding.py:67-79` already returns `None` and a single
  warning when the funding table is missing — so the silent-zero path
  fires on stale or missing data. Combined with the funding accrual
  being the dominant P&L component for CARRY, this is the silent-fault
  surface for "CARRY ledger says $X profit, reality is $X − Y unbooked
  funding cost". Recommend tightening to `log.warning` on any 0.0
  fallback that occurs because funding rows are missing, not because
  the window was empty.

## High — methodology / look-ahead

- [x] **R4_ETH's analytic simulator sizes the trade with Tuesday's daily
  close, but the live trade enters at Tue 20:00 — before Tue close.**
  `jplus/simulate.py:144-194`: `d` is the Wednesday key (`is_r4_e =
  dt.weekday() == 2`), `det_i = max(1, i-1)` is the Tuesday index, and
  `regime.classify_day(det_i, …)` uses Tuesday's daily close to set the
  regime. The contribution `c_r4e = weights["r4_eth"] * r4e_r` then
  multiplies the Tue→Wed return by that Tuesday-close regime weight.
  But the live entry handler at `services/jplus_live.py:164-229` calls
  `today_inputs()` at Tue 20:00 — `today_inputs()` runs the same
  decision loop, ends at `det_i = len(dates)-1` (the latest complete
  daily close = Monday's close at most, since Tuesday's close is in the
  future at 20:00 UTC), and so the live trade gets weighted by *Monday's*
  regime, not Tuesday's. **The simulator is using ~4 hours of
  post-entry data for regime classification.** Magnitude is small because
  regime classifications rarely flip overnight, but it's a real-direction
  inflation source not caught by the look-ahead canary at
  `tests/test_jplus_lookahead.py` (which tests cross-clock determinism,
  not data-availability-at-entry-time). Possible mitigation: the
  simulator could use `det_i = i - 2` (Monday's close) for R4_ETH
  specifically. Document and quantify before either fixing or accepting.

- [x] **`risk_caps.btc_long_cap_allows()` only checks PDO + CPR.** The
  cap variable is named `max_net_btc_non_core_pct` (`services/risk_caps.py:61`)
  but the SQL at lines 42-48 enforces it only on `strategy IN
  ('PDO_RETOUCH', 'CPR')`. ADX (15%, k=5×), FOMC (5%, k=10×), CARRY (8%
  delta-neutral but only the spot leg counts as BTC long), and the J+
  R4_BTC / R4_BTC_V2 / EMA_BTC sleeves are silently exempt. Worst-case
  concurrent BTC-LONG allocation under the actual cap: ADX 15 + FOMC 5
  + CARRY 8 + PDO 4.5 + CPR 2.5 + JPLUS_R4_BTC ≤6.5 + JPLUS_R4_BTC_V2
  ≤3.3 + JPLUS_EMA_BTC ≤21.7 = ~67% pre-leverage; at the stacked
  leverage of those sleeves the gross BTC long can hit 200–300% of
  variant capital. PORTFOLIO.md §5.1 shows P95 concurrent notional of
  118% and max 153% as a *backtest* observation — that's compatible
  with the cap doing nothing for the BTC-only direction. Either rename
  the variable to `max_net_btc_pdo_cpr_pct` to match what it does, or
  expand the SQL to enforce the documented intent.

- [x] **Selection bias from the R4 study findings.** The R4_BTC live
  config was changed from `Mon+Wed wk1-2 06→18` to `Mon wk1-2 06→18`
  on 2026-05-08, and R4_BTC_V2 / R4_ETH_V2 were spun out at
  `Wed+Fri wk1-2 04→14`. Per `tools/r4_study/findings.md`, the
  motivation is empirically defensible (Wed responds to the 04→14
  window better than 06→18; Wed+Fri is era-stable across pre/post
  Binance-perp/ETF, t=+4.6 over 402 fires), and a walk-forward at
  `walk_forward.py` keeps the OOS t-stat at +2.5. But the live config
  was *picked from a 7,500-config grid search of 57 in-every-year
  positive configurations* — i.e. it's the empirical top of a finite
  search, and the post-ETF era (2024-01 onward, ~2.3y) is too short
  for the post-ETF-only walk-forward to be conclusive (the findings doc
  acknowledges this explicitly). PORTFOLIO.md §7.1 acknowledges
  Aggressive-2.0-family selection bias but does not mention the more
  recent R4 windows-grid selection. Memory entry
  `project_r4_window_times_study.md` and the user feedback in
  `feedback_r4_post_etf_ride_with_monitor.md` confirm the strategic
  decision was deliberate ("ride it while it works, disable via
  expectancy monitor"). Worth recording as a §7 caveat addition so a
  later reader sees both selection bias sources cleanly.

## Medium

- [x] **`equity_metrics.sharpe` ignores the risk-free rate.**
  `tools/full_portfolio_report.py:116`, `backtest_runner.py:363`,
  `services/strategy_health.py:43`, `tools/tools_statistical_validation.py:80`
  — all four Sharpe calculators do `(mean / sd) × √365` with mean as the
  raw daily return. At a 4–5% Fed funds rate, that overstates Sharpe by
  ~0.5–0.7 (depending on series std). Not a structural defect — the
  convention is documented for crypto — but worth a sentence in
  PORTFOLIO.md §7.7 next to the existing "no deflated Sharpe" caveat.

- [x] **`tools_statistical_validation.correlation_vs_btc` uses perp BTC
  returns, but the variant trades spot-signal sleeves.**
  `tools/tools_statistical_validation.py:49-68` loads daily returns from
  `cd_futures_ohlcv` (Binance BTC perp). The v6 signals pivot to
  `cd_spot_binance` (see AUDIT_2026_05_04 perp→spot conversion). Spot
  and perp daily returns are very similar but not identical (basis
  drift adds ~10bp daily noise). Reported correlation against
  buy-and-hold is therefore slightly biased — magnitude tiny, but the
  inconsistency is worth a one-line fix when the tool is migrated off
  `variant_daily_returns`.

- [x] **AI_QUANT CVD includes today's still-forming day.**
  `services/ai_quant/cvd.py:50-58, 112-114` aggregates the daily CVD
  series including the bucket containing `clock.now_ts()`. The current
  AI_QUANT fire window is 00:05–00:15 UTC — so "today" at fire time is
  5–15 minutes of perp tape, essentially zero. That's safe for the
  current schedule, but the latest_daily_cvd_btc / latest_daily_cvd_z
  fields exposed to the model (`cvd.py:139-143`) carry the in-progress
  day's snapshot, not yesterday's closed day. If the AI_QUANT window
  ever shifts later in the day, those fields silently become
  "intraday-so-far" rather than "yesterday-closed". Document the
  invariant or align with the rest of context.py which explicitly drops
  the in-progress daily bucket (`services/ai_quant/context.py:89-93`).

- [x] **`_compute_defer_until_utc` clamps to 23:55 same day with no
  warning.** `services/ai_quant_service.py:86-98` — if the model
  requests `retry_in_hours=24`, the helper silently clamps to
  ≤23:55 today's UTC. The model is told the defer fired, but the
  realized defer is much shorter than requested. Acceptable for the
  current "defer within today only" semantic (also documented in the
  prompt), but the silent clamp can mislead the model's mental
  bookkeeping when the next decision's `decision_history` section
  (currently in BACKLOG.md) ships. Log when a defer is clamped so
  retrospective review can see it.

- [x] **Live banner test count drift.** README.md:314 and OPERATIONS.md:53
  both say "~518 tests". Actual count via
  `grep -c '^def test_\|^    def test_' tests/*.py` is **488 tests** in
  35 files. (Prior audits flagged this exact issue; the new drift is
  because tests were trimmed or consolidated post-Phase-5.)

- [x] **`register_p300.py` header comment is out of date.** Lines 8-23
  describe `JPLUS-CORE — 50% of capital, 2.5x inner leverage, regime-
  gated` as a single composition entry, `PDO-L-RF — 11%`, and "JPLUS-CORE
  contributes to variant_daily_returns (source='live_computed')". All
  three are wrong after the 2026-05-10 refactor + the 2026-05-12 PDO
  trim. The `composition` dict at lines 50-90 has the right values; only
  the header narrative is stale. A reader inspecting only the file
  comment learns a wrong story.

- [x] **`PORTFOLIO.md` §6 numbers cannot be regenerated cleanly.** The
  in-sample backtest table (Core +485.7%, Tactical +121.1%, Combined
  +294.8%, MDD -15.7%) is described as "v6 simulation, all-spot
  signals". Reproducing those numbers today requires running
  `backtest_runner.py` + `tools/full_portfolio_report.py`, but the
  latter has the Jensen's-gap defect (high-severity item above) — so
  re-running today produces compounded numbers that are systematically
  different from however the §6 figures were originally computed. Until
  the compounding bug is fixed, anyone validating §6 against fresh
  output will see a discrepancy with no documented explanation.
